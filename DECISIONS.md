## Multi-tenant conversion — 31 October 2026

- 2026-10-31 — Keep Drizzle rather than migrating the data layer to Prisma. The 22-table schema, its check constraints and the append-only audit triggers are already applied and covered by tests; a rewrite would consume the entire budget before a single multi-tenant feature existed, and would put the compliance-critical paths at regression risk for no user-visible gain. Decision taken with the user after presenting the trade-off.
- 2026-10-31 — Supabase Auth owns identity. Chase stores no password material; `app_users` mirrors the verified JWT so application tables can hold real foreign keys. `getUser()` revalidates on every request rather than trusting a decoded cookie.
- 2026-10-31 — Denormalise `business_id` onto every tenant-scoped table instead of joining through `debtors`. Scoping becomes one indexed predicate, and the column is what any future row-level policy would key on. Migration 0010 backfills from the parent debtor/call before setting NOT NULL, so it is safe on a populated database.
- 2026-10-31 — The browser never queries Postgres, so the PostgREST roles get nothing: RLS enabled and forced on every table, zero permissive policies, and all privileges revoked from `anon`/`authenticated` including default privileges. The app role holds BYPASSRLS. Adding a policy later must be deliberate.
- 2026-10-31 — The active workspace comes from a cookie that is re-checked against membership on every request, never from a request body or query string. A forged `chase_ws` value falls back to the user's own first workspace rather than erroring, and `?businessId=` on CSV import is now ignored.
- 2026-10-31 — R1 becomes a per-tenant permission rule. In demo mode it stays the `CALL_ALLOWLIST` safety rail; in production a debtor is callable only with a recorded consent basis attested by a named user at import, and an owner brief requires an OTP-verified owner number. The rule id is unchanged so historical compliance events stay readable.
- 2026-10-31 — Each workspace collects into its own UPI VPA with its own payee name. Chase is never a payment intermediary, which keeps vendor onboarding to one text field and avoids marketplace KYC. Razorpay Route remains available as a later upgrade.
- 2026-10-31 — One shared pair of Bolna agents for the platform, with per-call tenant variables, rather than provisioning an agent per workspace. Cheapest path that scales and keeps one webhook to maintain.
- 2026-10-31 — Invitations are email-bound, single-use and stored only as a SHA-256 hash with a 72-hour expiry. Because no transactional mail is wired yet, the API returns the link for an admin to pass on and the UI says so explicitly rather than implying an email was sent.
- 2026-10-31 — The workspace owner cannot be demoted or removed, so a workspace can never become ownerless. Ownership transfer is deliberately not an invitation flow.
- 2026-10-31 — The destructive sample-data reset now requires the owner role, a workspace that is actually the seeded sample, and a database containing no other business. On a real multi-tenant deployment it is therefore unreachable. `app_users` is excluded from its TRUNCATE so resetting sample data can never delete real accounts.
- 2026-10-31 — Pin Node >= 22 (`.nvmrc`, `engines`). The Supabase SDK requires a native WebSocket and fails on Node 20; Vercel already runs a newer runtime.
- 2026-10-31 — Make the Vercel Supabase cutover an explicit, three-key operation sourced from `.env.local`, with a dry-run default. The legacy `.env` and marketplace Neon variables must not be bulk-synced over tenant configuration.
- 2026-10-31 — Do not deploy the Supabase server key: current application paths do not use the admin client, and authentication needs only the public URL/key. Treat that key as optional in `configReport()`.
- 2026-10-31 — Show Google sign-in only when Supabase's public auth settings confirm that Google is enabled. The current project reports it disabled; displaying an unusable button misleads new users.
- 2026-10-31 — Stage the Supabase build on an unaliased, protected production deployment before promotion. Keep the public domain on its prior deployment until credential rotation and Auth redirects/SMTP configuration are complete.
